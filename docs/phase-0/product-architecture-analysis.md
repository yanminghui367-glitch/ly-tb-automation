# ly-tb-automation 产品架构分析

> 阶段：Phase 0 — Project Initialization  
> 状态：分析完成，等待业务资料确认；本阶段不进入代码开发。

## 1. 分析结论

本项目不应被设计成“AI 自动写文案工具”，而应被设计成一条**规则驱动、模板驱动、可人工复核、可批量恢复**的商品生产流水线。

第一阶段最重要的不是直接接入淘宝自动发布，而是先稳定完成：

```text
目的地数据 → 商品任务 → 标题与素材生成 → 商品包 → 人工审核 → 导出
```

商品包格式和淘宝实际发布字段验证后，再接入 RPA。这样可以避免过早绑定发布工具，并显著降低 Token、维护和返工成本。

核心架构原则：

1. 规则优先，AI 仅处理真正需要智能判断的例外。
2. 商品生成与淘宝发布彻底解耦。
3. 内部统一使用商品包作为发布输入。
4. 模板选择必须可复现，不使用不可控的纯随机。
5. 每个商品独立任务化、版本化、可重试。
6. 首版保留人工审核。
7. SQLite 足以支持 MVP，不提前建设复杂基础设施。
8. 先验证淘宝真实字段，再开发 RPA。
9. 图片、标题和详情规则全部配置化。
10. 自动化失败必须有日志、截图和人工恢复入口。

## 2. 当前业务流程图

### 2.1 销售业务流程

```text
全球目的地与服务资源
        ↓
选择国家 / 城市
        ↓
制作淘宝商品入口
        ↓
用户通过淘宝关键词搜索并进入商品页
        ↓
旺旺咨询日期、人数、服务内容
        ↓
人工询价、核算成本并报价
        ↓
客户下单成交
        ↓
匹配境外服务资源
        ↓
服务履约
        ↓
售后与评价管理
```

该模式的本质是利用大量国家级、城市级商品链接获取搜索流量，再通过咨询完成非标准服务交易。商品页面主要负责覆盖目的地关键词、展示八类服务、建立信任、引导咨询，并避免对价格、行程和资源作出过度承诺。

### 2.2 商品生产目标流程

```text
目的地数据库（国家、城市、关键词、图片状态）
        ↓
创建国家级 / 城市级商品任务
        ↓
规则生成两个标题候选并选择正式版本
        ↓
确定性选择主图、副图、详情首图与城市素材
        ↓
程序渲染图片与固定详情页
        ↓
组合淘宝发布字段
        ↓
质量检查（字段、标题、图片、重复度、禁用词、素材）
        ↓
人工预览与审核
        ↓
生成标准商品包
        ↓
发布适配器（Excel / CSV、RPA、未来官方接口）
        ↓
淘宝后台
        ↓
记录成功、失败、待重试或人工处理结果
```

## 3. 系统模块划分

系统划分为八个通过稳定数据结构连接、彼此可替换的核心模块。

### 3.1 目的地数据中心

管理国家、城市、中英文名称、归属关系、时区、启用状态、优先级、核心城市标记、搜索关键词、图片资源和商品生成状态。

- Excel 是非技术运营人员的数据录入入口。
- SQLite 是系统内部正式数据源。
- 导入时校验并输出新增、更新、重复和非法字段报告。
- 国家和城市使用固定唯一 ID，不能只依赖中文名。

### 3.2 商品规划与任务中心

将每个商品作为独立、可追踪、可重试的生产单元。任务记录目的地、商品层级、规则版本、服务类型、优先级、状态、重生成权限和错误原因，避免单次脚本失败后无法判断完成范围或覆盖人工修改。

### 3.3 规则与标题生成中心

每个商品默认由规则生成两个候选标题，例如：

```text
城市 A：{城市}中文导游地陪翻译包车接送机一日游商务陪同服务
城市 B：{国家}{城市}旅游地陪中文导游翻译接送机包车定制服务
国家 A：{国家}旅游地陪中文导游翻译包车接送机定制服务
国家 B：{国家}当地导游地陪一日游商务陪同展会翻译服务
```

采用三层机制：规则模板生成、关键词词典程序化调整、核心或特殊目的地的低频 AI 优化。标题长度、关键词优先级、名称组合、服务词顺序、禁用词、重复词、特殊地区和默认选择策略均配置化。两个版本仅是候选，不开展大规模 A/B 测试。

### 3.4 素材资产管理中心

统一管理原始城市图片、主图模板、副图模板、详情首图、字体、Logo、图标、服务类型图以及授权信息。

```text
assets/
├── templates/
│   ├── main/
│   ├── secondary/
│   └── detail/
├── city_images/
│   └── {country_code}/{city_slug}/
├── common/
│   ├── icons/
│   ├── logos/
│   └── fonts/
└── generated/products/
```

模板除视觉文件外，还应包含机器可读配置，描述画布、背景和文字变量的坐标、字号、颜色与最大宽度，使版式调整无需修改 Python 代码。

### 3.5 图片与详情页渲染引擎

使用 Pillow 完成裁剪、缩放、模板合成、国家/城市文字替换、字号自适应、长名称换行、Logo/图标叠加、格式转换、压缩和详情长图生成。

默认使用确定性模板选择：

```text
template_index = hash(product_id) % template_count
```

同一商品重跑时选择不变，便于复现；人工指定模板时，人工选择优先。

### 3.6 商品包生成器

将标题、图片、详情和淘宝字段组合为与发布工具解耦的标准商品包：

```text
output/products/CITY-JP-TOKYO/
├── manifest.json
├── product.xlsx
├── title_candidates.txt
├── main_images/
├── detail_images/
├── preview/preview.html
└── logs/generation.json
```

RPA 只读取审核通过的商品包，不直接读取数据库多张业务表。商品包可人工检查、交付外部运营、重新发布并审计生成时使用的标题、模板和素材。

### 3.7 质量检查与人工审核中心

自动检查标题空值/长度/重复/禁用词，名称正确性，图片数量/尺寸/格式/损坏/文字溢出，详情必要提示，淘宝必填字段，重复商品，素材目的地匹配和授权记录。

状态流转：

```text
DRAFT → GENERATED → VALIDATION_FAILED / WAITING_REVIEW
      → APPROVED / REJECTED → READY_TO_PUBLISH
      → PUBLISHED / PUBLISH_FAILED
```

审核后台支持候选标题选择、手工修改、图片预览、模板切换、图片重生成、批量批准和错误查看。

### 3.8 发布适配器与记录中心

统一发布接口建议包含：

```text
Publisher
├── validate(product_package)
├── prepare(product_package)
├── publish(product_package)
├── query_result(publish_job)
└── retry(publish_job)
```

实现可包括 `ExcelExportPublisher`、`ManualPackagePublisher`、`RpaPublisher` 和未来的 `OfficialApiPublisher`。发布记录保存内部商品 ID、渠道、任务号、淘宝商品 ID、商品包版本、状态、截图/日志、失败步骤、原因及重试信息。

## 5. 自动化流程设计

### 5.1 数据准备

运营人员填写目的地 Excel，系统完成字段校验、重复检测、SQLite 写入和导入报告。错误必须定位到行与字段，例如“第 26 行：国家代码 FR 不存在”，不得静默跳过。

### 5.2 商品任务创建

支持单个国家、国家全部城市、优先级批次、仅核心城市、仅补缺失商品和审核失败重生成。系统先创建任务，不立即发布。

### 5.3 规则化内容生产

```text
读取商品任务 → 获取目的地与服务配置 → 生成标题 A/B
→ 选择模板 → 检查城市素材 → 渲染图片和详情
→ 生成淘宝字段草稿 → 输出商品包
```

仅在核心城市且明确标记、两个规则标题均不合格、特殊名称无法处理、人工点击优化等条件下调用 AI。图片重渲染和商品包重新导出不得触发 AI。

### 5.4 自动质检与人工审核

- **ERROR**：缺少目的地/主图/必填字段、图片损坏、标题为空或生成失败；阻断发布。
- **WARNING**：标题接近上限、清晰度低、重复度高、授权不完整或模板近期使用过多；由人工决定。
- **INFO**：使用默认模板、规则标题或非核心城市等提示。

首批商品逐件审核；稳定后普通城市可批量审核；国家级、核心城市和 AI 内容始终人工审核。修改后重新进入审核，已发布商品不得被普通重跑静默覆盖。

### 5.5 RPA 发布

RPA 按商品包逐件处理：检查登录、进入发布页、选择类目、填写标题/价格/属性、上传图片和详情、执行页面校验、保存草稿或发布、获取结果、截图并回写状态。

验证顺序：

1. 只打开发布页。
2. 自动填写但不保存。
3. 自动填写并保存草稿。
4. 人工检查草稿。
5. 小批量正式发布。
6. 稳定后提高自动化比例。

稳定性措施包括元素定位优先、每步超时、关键截图、文件预检、发布前复核、有限重试、断点恢复、发布限速，以及登录失效/验证码时转人工处理。不得自动绕过淘宝验证码或风控。

## 6. 技术选型建议

| 领域 | MVP 选择 | 说明 |
| --- | --- | --- |
| 后端 | Python | Excel、图片、SQLite、RPA 生态成熟，适合低并发内部工具 |
| API | FastAPI 单体应用 | 管理导入、任务、生成、预览、审核、导出与发布状态 |
| 数据库 | SQLite | 单机、少量运营人员、数千至数万商品；出现真实并发锁竞争后再评估 PostgreSQL |
| Excel | openpyxl | 固定模板读写优先；复杂批量清洗确有需要时再引入 pandas |
| 图片 | Pillow | 足以支持裁剪、文字、合成、压缩与长图；复杂版式以后再评估 HTML/SVG |
| 前端 | Jinja2 + Bootstrap/轻量 CSS + 少量原生 JS | 页面少、部署简单；复杂交互出现后再考虑 Vue/React |
| 后台任务 | 数据库任务表 + 单独 Python Worker + 系统定时任务 | 暂不引入 Celery 和 Redis |
| 配置部署 | virtualenv + `.env` + SQLite + 本地资产 + 每日备份 | 可提供 Docker，但不作为非技术人员使用前提 |

至少保留系统日志、生成日志和发布日志，包含 `product_id`、`job_id`、操作、状态、耗时、错误码和时间。建立稳定错误码，如 `DESTINATION_NOT_FOUND`、`SOURCE_IMAGE_MISSING`、`TITLE_TOO_LONG`、`IMAGE_RENDER_FAILED`、`TAOBAO_LOGIN_EXPIRED`、`RPA_ELEMENT_NOT_FOUND`、`PUBLISH_RESULT_UNKNOWN`。

AI 默认关闭自动调用；必须显式触发并缓存相同输入，记录提示词版本、模型和输入输出，设置单次与每日预算，失败时回退规则结果。

## 7. MVP 开发范围

### 7.1 MVP 目标

在不依赖淘宝自动发布的情况下，稳定批量生成**可审核、可追踪、可导出**的完整商品包。

### 7.2 必须包含

1. 国家、城市、服务类型、Excel 导入、校验、启停和优先级。
2. 国家级/城市级商品任务、批量创建、状态查看和失败重试。
3. 两个规则标题、长度与去重校验、人工选择和编辑。
4. 城市图片目录、模板注册、素材存在性/尺寸检查和预览。
5. 一套主图、两套副图、两套详情首图及确定性选择。
6. 固定详情页、八类服务、咨询流程、价格/范围说明和目的地变量。
7. 标题、图片、必填字段和素材缺失质检。
8. 商品列表、预览、审核、退回、重生成和商品包下载。
9. `manifest.json`、Excel/CSV、图片、生成日志与 HTML 预览输出。

### 7.3 暂不包含

全自动正式发布、复杂 Agent、多模型路由、全城市 AI、动态定价、咨询自动回复、资源调度、履约、订单管理、多租户、微服务、Redis、Celery、Kubernetes、复杂前端、大规模 A/B 测试及绕过验证码/风控。

### 7.4 验收建议

使用 3 个国家、每国 5 个城市，共 18 个商品（3 个国家级、15 个城市级）进行验收：

1. 一次批量创建全部商品。
2. 每件生成两个合法标题和完整图片。
3. 同一商品重生成时模板选择稳定。
4. 缺图时错误清晰，单任务失败不影响其他任务。
5. 可人工修改、批准并独立导出商品包。
6. 所有生成行为可追踪且全流程无需 AI。
7. 已批准内容不被普通重跑静默覆盖。
8. 数据库与素材可备份恢复。

## 8. 后续迭代路线

### Phase 0：业务与字段确认（当前阶段）

确认商品矩阵、标题规则、淘宝类目与必填属性、真实发布页面、图片/详情限制、首批目的地、素材授权、试验账号与测试商品。输出产品架构、字段清单、数据字典、模板设计稿和 MVP 验收标准。

### Phase 1：离线商品生产 MVP

完成 `Excel → SQLite → 商品生成 → 人工审核 → 商品包导出`。先人工发布少量商品，发现真实字段问题。

### Phase 2：淘宝发布字段适配

建立内部字段到淘宝页面字段的完整映射，确认类目、属性、价格、库存、发货/服务承诺、图片顺序、详情方式、个性化定制字段、草稿能力和商品 ID 获取方式。

### Phase 3：RPA 概念验证

用 10 个已审核商品统一评估影刀、UiBot 或其他候选工具的元素定位、图片上传、富文本、异常恢复、日志、人工接管、部署、成本、升级风险和集成能力。阶段目标仅为“商品包 → 自动填写 → 保存草稿”。

### Phase 4：小批量自动发布

每批 5～10 个，由人工启动，自动填写、保存/发布、截图和记录；失败可重试。重点观察登录、验证码、页面变化、上传失败、审核违规和重复发布。

### Phase 5：规模化生产

增加批次与优先级队列、素材缺口看板、批量审核、定时生成、多 RPA 节点、发布限速、重复检测、失败归类及备份恢复。

### Phase 6：运营优化

基于真实咨询和搜索数据调整城市优先级与标题规则，淘汰低质量模板，为核心/特殊城市使用 AI，增加版本管理、已发布商品巡检和违规状态监控。

## 9. 系统边界

系统负责目的地、模板与素材管理，商品内容生成、审核、商品包输出、发布驱动和发布结果记录。

第一阶段不负责复杂报价、资源承诺与调度、履约、客户纠纷、绕过验证码/风控或判断淘宝政策合规性。未来 CRM、资源调度或履约系统应作为独立模块，通过商品 ID 或订单 ID 关联。

## 10. Phase 0 待确认信息

### P0：直接影响数据模型和发布
