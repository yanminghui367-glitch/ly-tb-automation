最小方案：打开弹窗时固定批次 ID、模式、商品 ID 集合和确认范围指纹；提交前以权威状态重查，变化则关闭原确认并要求重新核对，禁止静默切换。开始和继续与现有重试范围检查保持一致。若仅前端封闭不足，再明确后端校验最小范围，不能先改再请求批准。

收益：避免操作者确认 A、请求却落到 B。影响：新版工作台开始 / 继续确认和产品接口的范围检查；真实执行器不需要重写。验证：两个独立测试客户端、旧批次完成后新批次进入、DRY_RUN / LIVE 切换、同 ID 状态变化、丢响应重放，均检查目标与原确认一致且只调度一次。

### 优先 2：A01 原商品关联核验

最小方案：为 RESULT_UNKNOWN 增加受控“关联已发布商品”流程。操作者提供 ID → 原店铺中只读查询并匹配原冻结标题、价格、库存和时间证据 → 保存核验证据 → 原任务回写结果。零 / 多匹配或证据不足继续阻塞。**不得手动直接标成功，不再次提交；关联完成也不自动启动余下批次。**

收益：解除“平台已有商品、本地无法恢复”的死结，减少重复发布冲动。影响：恢复接口、原任务检查点 / 审计事件、核验结果回写及对应 UI。风险高，需要分模块复测断电、跨店 ID、重复 ID、错商品和截图失败。

### 优先 3：A02 证据真实性

最小方案：每次截图使用唯一文件名，成功保存后才登记路径；失败记录明确的截图错误和时间，不继承旧图。状态保存不能依赖截图成功，已核验任务也不能因证据文件写入失败再次提交。需要批准冻结 `source-workflow.mjs` 的这一小段增量。

这是合成环境的服务器投影耗时，**不是页面加载时间或真实自动上架耗时**，不含实际登录检查、700 份图片、长历史日志和多台机器网络。没有为此修改性能逻辑，也没有提速百分比。

调用路径风险：每个 SSE 连接每 2 秒生成执行快照；已有 pending 防止同连接重入，但不同连接仍重复投影。产品关系变化时前端额外读取完整 OS 状态。可以后续量化多客户端共享快照与按需字段的收益；本轮没有通过减少安全检查或提高发布并发“提速”。此前堆内存耗尽的根因在本轮没有复现或解决。

已实际验证：符合缺失 ID 条件时，隔离界面首次打开恢复弹窗即可看到原因和核对标题；报价脚本增加等待后本次 31 项检查通过。未进行长期重复运行，不能据此声称测试从此不会偶发失败。预计减少重复点击和排障，但没有用户耗时实测，节约分钟数尚未量化。

## 【风险】【下一步】

本轮不放行无人值守或多客户端并行操作正式批次。优先单独审批 A03，再审批 A01；A02 随下一次受控内核修复纳入。旧完整 UI 套件需按当前页面重新对齐，长时间内存与第二台设备另设一次明确隔离的验证。
