# 能力判断与交接协议

## 如何决定由谁做

| 事实 | 总负责人处理 |
| --- | --- |
| 已定位的小缺陷，工具/文件归属/验证条件具备 | 亲自修复或交原执行者完成，选能最快提供可靠结果的路径 |
| 专项工作可独立、文件不冲突、对方已有背景 | 交对应agent，写清目标和验收，不要求重做已通过的部分 |
| 原agent缺工具/权限，总负责人具备 | 接管需要该工具的步骤，再把结果交回；不让用户充当搬运工 |
| 涉及多个正在修改的共享入口或运行版本切换 | 总负责人整合，逐项对照内容/基线/测试；不得代替其他作者盲目冻结 |
| 问题未复现、日志不足但可以安全复现 | 保留未知，先构造隔离复现或补只读证据，不靠猜测修改正式流程 |
| 未知提交、同一请求回执丢失 | 查原请求/run/商品ID和持久记录，先核验，不换新请求重发 |
| 验证码、错店、供给/真实业务字段缺失 | 停受影响的发布动作，继续无依赖技术工作；只向用户补尚缺事实或人工处理 |
| 没有线程接口，只有共享文件 | 交接文件可准备；状态为“待接收”，不能写“已通知/已接手” |

不按虚构的agent能力评分派活。核对其实际任务、工具、可访问资料、文件编辑范围和已有成果；角色名字只说明责任，不证明技术权限。对关键修复的独立复核可另委派实际QA agent。

## 从报告到闭环

**提交 → 总负责人分诊 → 接收方确认 → 修复/补证 → 实际复核 → 集成/加载核对 → 关闭或明确阻塞。**

现有 `TASK_BOARD.md` 管理任务状态继续使用“待开始、进行中、待复核、已验收、阻塞、需返工、取消”。交接另记“待接收/已接收”，不写进网站任务枚举，也不创建第二套发布队列。

交接前列明未提交修改和已有版本；接管人确认后原编辑者停止对应文件写入。交付时比对基线是否漂移，漂移则重审受影响部分。交回不丢失原run、manifest、尝试次数、原请求和失败证据。共享运行服务的重启、专用Chrome和执行控制只指定一个责任人。

能从仓库补齐的信息由总负责人补齐，避免因表单字段不完整来回退件。缺少复核者时写待指派；缺少平台事实时写具体缺项；两者都不冒称通过。

## 最小交接包

可存到本次专项输出目录或 `docs/operations/handovers/<任务ID>.md`，在原任务表只登记一条入口。敏感运行证据留在本地忽略目录，交接文件只给必要路径/哈希。

```markdown
# <任务ID> <具体问题/结果>
核验时间：
项目根/副本：
提出者（真实agent/聊天标识；未知写未知）：
当前执行者 → 接收者：
任务状态：进行中/待复核/阻塞等；交接：待接收/已接收

目标与完成条件：
当前现象、影响及优先级依据：
范围：店铺/商品或批次/运行版本；无业务动作写无
固定身份：round/window/manifest/run/requestId（适用时填写）
允许编辑文件与唯一编辑者：
原有未提交修改及输入版本/哈希：

事实与证据路径：
已尝试的方法、实际结果和仍未知的部分：
交付文件/差异：
验证命令、结果、版本及证据限制：
是否已集成/运行已加载/平台已核验（分别记录）：
接收方确认及下一步：
复核者/结论/尚缺条件：
维护回退依据（涉及部署或数据时）：
```

## 本项目典型交接

- 子agent称“按钮改了但网站没变化”：总负责人先比对静态资源/运行版本/接口。若只是未加载，按既有维护授权整合；若后台保护拒绝，查具体原因。不要再写第二个跳过入口或删除提交保护。
- “名古屋已上架但一直待核验”：定位原run、商品ID和后台核验记录；可修已证实的搜索遮挡或查询问题，再核验原商品，不能再提交一条制造成功。
- “环球资料导入入口仍是五洲”：先保留原素材和两个店铺的记录；由实现者完善服务端上下文与UI同店绑定，原网站操作agent接验收。仅登录成功不能代替新店适配。测试证明隔离后再按原授权核对导入对象，不直接改旧任务shopId。
- “多个聊天都改了kernel-lock”：整合者接收各自文件和测试版本，只登记已审核内容；保留未审核差异。历史已移除的页面数量限制不能用旧报错重新启用。
