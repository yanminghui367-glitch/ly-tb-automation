# 星途 Travel OS · 已实现的本地工作台

核对日期：2026-09-27。这里保存从本机已运行项目筛选的代码快照，包含未提交但已核对的产品层增量；**不替换仓库根目录原有 FastAPI 系统，也未实现两套系统之间的数据同步**。

项目的实际价值是：把已准备的旅游商品资料，连接到可检查、可暂停、可恢复、可追溯的淘宝发布流程。不是无人值守700条发布承诺，也不是AI生图系统。

## 本机首次安装

前置：Windows、Node.js 24+、Python 3.10+（`python`在PATH）、Google Chrome。已有依赖版本锁定于 `workbench/package-lock.json`。

在**本目录**打开终端，仅首次安装执行：

```powershell
npm ci --prefix workbench
npm run check --prefix workbench
npm test --prefix workbench
```

日常双击 `启动上架工作台.vbs`，访问 `http://127.0.0.1:4318/`。点击“打开工作台”进入 `/travel-os.html#overview`；旧操作台 `/index.html` 保留。启动器会尝试打开项目专用Chrome，登录由操作者处理。启动器日志保留在本目录 `.runtime/launcher/`，不上传。

已有另一个4318服务时先确认使用哪一套；不要同时启动两个生产副本。双击启动依赖首次安装完成，不能把克隆仓库等同于已配置好本机环境。

操作顺序：检查执行浏览器/人工登录 → 资料设置导入实际Excel与图片 → 校验和预览 → 核对店铺、范围与模式 → 手动开始 → 有验证时人工处理 → 检查恢复条件 → 查看平台结果。默认执行许可关闭，准备单和选中目的地入口不会自动发布。

## 安全与恢复边界

- 原表只读；生成的快照、数据库、日志和截图写入本机运行目录。
- 验证码/滑块只保存断点并暂停，由用户在执行浏览器手动处理。普通等待人工不等于验证码。
- 成功商品在原状态库内禁止重复发布；提交结果不明只允许先核验，不直接重发。重试入口保留原模式，LIVE重试会产生真实发布，必须核对范围。
- 暂停请求不等于已安全暂停；必须等现有操作完成、断点保存及状态确认。
- **本包不包含生产状态库。新克隆没有原店铺的历史防重记录，不能直接用新空库接着发布同一店铺。** 继续生产应使用原工作区及其原状态库；迁移需操作者单独备份/迁移业务状态并核验，登录在新电脑重新完成，均不经GitHub传递。
- 执行内核10个文件保持原字节，`workbench/kernel-lock.json`校验；本目录`.gitattributes`防止Git换行转换破坏锁。`baselineCommit`指原本机历史，不是本次远端提交。

## 验证与限制

本次导出副本：`npm ci`成功，语法检查通过，工作台167项测试通过；另核对14项Python测试。全新空目录进行了8项只读启动/页面检查：无商品、无历史、无活动任务，内核哈希通过，无写请求，无执行Profile创建。详见 [`VERIFICATION.md`](VERIFICATION.md)。本次没有真实发布。

历史资料支持单商品、5条和20条真实发布流程；5条包含两次人工滑块处理，20条包含修复、重试和异常重启恢复。不是无人干预压测，也不能据此保证所有店铺或700条一次成功。

尚存限制：

1. 商品池字段、素材命名和发布属性适配针对原已验证店铺；新增店铺管理可用，自动发布不具备通用多店铺适配。
2. 部分内核默认路径仍指原机D盘，应在资料设置填写本机实际路径；本次不为上传而改写冻结内核。
3. 已知素材库定位/上传等待/新增表单URL校验有历史失败，增加重试按钮不等于根因修复。
4. 既有20条验收结果为后台“出售中”，不能称全部“进入仓库”；记录页保留实际证据区别。
5. 源图片错配与同名目的地关联需要人工补齐；文件数量正确不等于内容或供给审核通过。
6. 非无人值守、非多用户权限系统。内网策略代码可用，Windows计划任务、防火墙和本机网络配置没有上传；内存增长根因、跨设备/系统重启后的长期稳定性未完成全面验证。

`engine/v2/`同时保留早期配置驱动CLI及其历史README，平台实绩来自上方工作台执行链路，不能自动归因于CLI模板。若单独使用CLI，另在`engine/v2`执行`npm install`。其模拟测试与真实发布成绩分开。
